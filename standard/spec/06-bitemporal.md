# BPA Standard — Bitemporal Semantics (TIME) `[Profile: Bitemporal]`

> BPA 1.0.0-rc11. Generated by `standard/tools/build_release.py` from `docs/50-system/30-standard/06-bitemporal.md`; do not edit. Clauses outside this release are omitted.

### STD-TIME-001 — Transaction time assignment
- **Clause:** The implementation MUST assign `tx_time` to each commit at flush from a hybrid logical clock (HLC). The value MUST be greater than the `tx_time` of the branch head it extends. When the physical clock is behind the HLC by more than the configured bound (default 1 s), the implementation MUST emit `NOD.CLOCK_SKEW`. Clients and logic MUST NOT supply `tx_time`.
- **Grammar / Schema:** —
- **Conformance vectors:** VER-CONF-1700…1714
- **Satisfies:** FR-TIME-011, FR-TIME-012, FR-TIME-013
- **Notes:** The HLC is represented as an RFC 3339 instant with microseconds, using the logical counter to break ties in the last microsecond digits.

### STD-TIME-010 — Valid-time periods
- **Clause:** Each Definition version has a valid period `[from, to)`, with `to = null` meaning open. The granularity is `date` or `instant` per class. Date bounds are interpreted in the VAE business time zone (STD-FND-024).
- **Grammar / Schema:** —
- **Conformance vectors:** VER-CONF-1715…1724
- **Satisfies:** FR-TIME-021, FR-TIME-023
- **Notes:** —

### STD-TIME-011 — The timeline of an object
- **Clause:** For object o on branch X, the timeline `TL(o, X, t)` at transaction time t is a list of non-overlapping segments `(period, version)`, sorted by period start. It MUST be computed by applying, in commit order, the timeline operations of all commits on X's history with `tx_time ≤ t`, starting from an empty timeline:

  | Operation (valid part of an update) | Effect on the timeline |
  |---|---|
  | `create(v, from)` | insert `[from, ∞)` → v; the timeline must be empty |
  | `supersede_from(v, d)` | let `e` = the start of the first segment starting after d, or ∞; replace `[d, e)` with v (splitting any segment that contains d) |
  | `set_period(v, a, b)` | if any existing segment intersects `[a, b)` without lying entirely inside `[a, b)`, reject with `TIME.OVERLAPPING_VALIDITY`; otherwise remove the segments inside `[a, b)` and set `[a, b)` → v. `set_period` therefore fills gaps and replaces whole segments; it never splits a segment (DEC-032, OQ-004) |
  | `replace_future(v, d)` | remove every segment starting at or after d; truncate the segment containing d at d; insert `[d, ∞)` → v |
  | `end(d)` | truncate the segment containing d at d; remove every later segment; the object is ended from d |

  A plain update without valid-time parameters is `supersede_from(v, today)` for date granularity, or `supersede_from(v, tx_time)` for instant granularity.
- **Grammar / Schema:** —
- **Conformance vectors:** VER-CONF-1725…1774
- **Satisfies:** FR-TIME-022, FR-TIME-025, FR-TIME-051
- **Notes:** The table is the formal model of the bitemporal update semantics. The implementation's `temporal_index` is a materialisation of it (AR-016).

### STD-TIME-012 — As-of resolution
- **Clause:** Reading o on X with `asof = a` and `time = t` MUST return the version of the segment of `TL(o, X, t)` that contains a. If no segment contains a, o is not found at those coordinates (`QRY.NOT_FOUND_AT_TIME` when o exists at other coordinates). The defaults are `a = now` (as a date in the business time zone for date granularity) and `t = head`.
- **Grammar / Schema:** —
- **Conformance vectors:** VER-CONF-1775…1799
- **Satisfies:** FR-TIME-031, FR-TIME-051
- **Notes:** Future-dated versions become effective purely by resolution. No job is needed.

### STD-TIME-013 — Consistent coordinates across references
- **Clause:** When a read or query follows references, targets MUST be resolved at the same `(asof, time)` as the source object, unless the reference pins a version. Stored references carry no version pin (STD-ADDR-001); the exception applies to references given with a `commit` or `tag` selector in a query (STD-ADDR-002). A target without a segment at `asof` is omitted (DEC-041).
- **Grammar / Schema:** —
- **Conformance vectors:** VER-CONF-1800…1809
- **Satisfies:** FR-TIME-032
- **Notes:** —

### STD-TIME-014 — Range queries
- **Clause:** A valid-range query `[a, b)` at time t MUST return the segments of `TL(o, X, t)` that intersect `[a, b)`, clipped to it. A transaction-range query `[c, d)` MUST return the commits on X with `c ≤ tx_time < d` that changed o, with their timeline operations. Valid bounds use the granularity of the class, and an empty valid range is rejected (`MODEL.INVALID_VALUE`). The commits on X are those of its first-parent history; changes made by relationship rules report their operation, and merge and revert commits report `merge` and `revert` (DEC-041).
- **Grammar / Schema:** —
- **Conformance vectors:** VER-CONF-1810…1824
- **Satisfies:** FR-TIME-033, FR-QRY-051
- **Notes:** —

### STD-TIME-015 — Evaluation evidence
- **Clause:** Every bitemporal answer MUST carry `evaluated_at`: the commit ID resolved for each branch consulted. Repeating the request with those commit IDs MUST return identical results. `evaluated_at` maps each branch consulted, including the branches of a parent line (STD-VER-080), to its commit ID; a request that carries `evaluated_at` uses exactly those commits and no other selector (DEC-041).
- **Grammar / Schema:** —
- **Conformance vectors:** VER-CONF-1825…1829
- **Satisfies:** FR-TIME-034
- **Notes:** —

### STD-TIME-020 — Bitemporal inclusion of entries
- **Clause:** An entry e is included in a ledger read at `(asof = a, time = t)` if and only if `e.valid_at ≤ a` (compared at the class granularity) and e's commit has `tx_time ≤ t`. Balance projections MUST produce results equal to aggregating exactly the included entries.
- **Grammar / Schema:** —
- **Conformance vectors:** VER-CONF-1830…1849
- **Satisfies:** FR-TIME-024, FR-LEDG-032
- **Notes:** —

### STD-TIME-021 — Projections
- **Clause:** A projection MUST be an object of the genesis Definition class `Projection` (`DAT-Projection`) that folds the entries of one ledger class, its `source`. It groups them by the values of the fields in `group_by` (ledger key or body fields) and computes `aggregates`, each `{fn, field, as}` with `fn` one of:
  - `count`, the number of entries;
  - `sum`, `min` or `max` of a decimal, integer or money field;
  - `last`, the field of the last entry in `(valid_at, cseq, seq)` order.

  A read of a projection at `(asof = a, time = t)` MUST equal the fold of exactly the entries STD-TIME-020 includes, for any branch and point in time. A projection is maintained `sync`, in the commit that appends the entries, or `async`, after the commit:
  - every read MUST return the `watermark`, the commit up to which the projection is maintained; a `sync` projection is maintained up to the snapshot;
  - an `async` read MUST equal the fold at the watermark;
  - a read MAY ask for `at_least` a commit sequence and wait up to a timeout, failing with `QRY.WATERMARK_TIMEOUT` when the watermark stays below it.

  A projection MUST be rebuildable from the committed entries without a read seeing a missing or partial projection: a rebuild switches atomically to a result equal to the fold at the branch head.
- **Grammar / Schema:** `DAT-Projection`
- **Conformance vectors:** VER-CONF-1930…1959
- **Satisfies:** FR-LEDG-031, FR-LEDG-033, FR-ANL-021, FR-ANL-023, DSN-DVM-420, DSN-DVM-422
- **Notes:** Since 1.0-rc9 (DEC-098):
  - **Declaration.** A `source` that is not a ledger class, a field in `group_by` or `aggregates` that the class lacks, a field of `sum`, `min` or `max` that is not numeric or money, an unknown `fn` or a repeated `as` fail with `MODEL.INVALID_VALUE`; two live projections with the same `name` fail with `MODEL.CONSTRAINT_VIOLATED`.
  - **Results.** A decimal sum keeps the largest input scale. A money aggregate gives one money value per currency in currency order, at the currency's minor units, as close artefacts do (STD-KIND-026). `min` and `max` compare numbers numerically. Groups are `{key, entries, values}` in the order of the canonical JSON of `key`.
  - **Entries.** Only entries of the `source` class count, not entries of its subclasses. Projections over Definition versions (DSN-DVM-422) are not in this release.
  - **Changes.** A changed declaration applies to every read after the commit that changes it: the projection is rebuilt.
  - **Adapter operations.** `read_projection` reads as `read.projection` (STD-ISA-037) at explicit coordinates; `projection_lag {branch, projection, cseq}` stops the maintenance of an `async` projection after commit `cseq` (null resumes it), so that vectors can observe a lagging watermark; `rebuild_projection {branch, projection}` rebuilds it and returns `{projection, groups, watermark}`. A lag on a `sync` projection fails with `MODEL.INVALID_VALUE`.
  - **Implementation.** DSN-DVM-420 keeps balance deltas and checkpoints; the standard fixes the results only.

```yaml
DAT-Projection:
  name: { type: text, required: true, description: "unique among the live projections of the branch" }
  source: { type: text, required: true, description: "name of the ledger class folded" }
  group_by: { type: list, required: false, description: "field names; no field gives one group" }
  aggregates: { type: list, required: true, description: "{fn, field, as} items; fn count | sum | min | max | last" }
  mode: { type: enum, required: false, description: "sync | async (default sync)" }
  description: { type: text, required: false, description: "purpose" }
```

### STD-TIME-030 — Retroactive changes
- **Clause:** A timeline operation is retroactive when it affects any part of the timeline before the start of the current business day. The commit MUST record, per retroactive change, the affected valid range.
- **Grammar / Schema:** —
- **Conformance vectors:** VER-CONF-1850…1859
- **Satisfies:** FR-TIME-041
- **Notes:** —

### STD-TIME-031 — Impact set
- **Clause:** For a retroactive change of object o over the valid range R, the impact set MUST be the transitive closure, over derivation records (STD-TXN-030), of every object version and entry whose derivation used a version of o for an `asof` inside R that is superseded by the change. A version v is superseded for an `asof` a when v is the version at a before the change and not after it. The closure follows every derivation record on the branch whose inputs name an impacted version or entry, at any `asof` (DEC-041).
- **Grammar / Schema:** —
- **Conformance vectors:** VER-CONF-1860…1874
- **Satisfies:** FR-TIME-042
- **Notes:** —

### STD-TIME-040 — Rule binding record
- **Clause:** Each commit MUST reference a `DAT-RuleBinding` that lists the content IDs of:
  - class versions, extension versions and lifecycle versions;
  - governance sheets and decision tables;
  - policies and logic assets.

  These are the items evaluated to validate, decide or compute any change in the commit. `classes` lists the declared class versions of the linearizations of the classes of the changed objects and entries, and the versions of the extension objects applied to them; `logic` lists the logic of the commit's derivation records (STD-TXN-030). Sheets, tables, policies and guards are bound with the Governance profile (DEC-041).
- **Grammar / Schema:** `DAT-RuleBinding`
- **Conformance vectors:** VER-CONF-1875…1884
- **Satisfies:** FR-TIME-061, FR-FLOW-032
- **Notes:** Since 1.0-rc3 (DEC-071): `guards` lists the guard evaluations of the transitions and ports the commit's process executed, `{guard: "<transition>/<name>" | "<port>/<index>", result: true}` (a failed guard stages nothing, so only passed guards reach a commit); `classes` lists the version of the lifecycle object of a changed object's class as `{class: Lifecycle, object_id, class_version}`. Since 1.0-rc7 (DEC-084): `sheets` lists the versions of the governance sheets that apply to the objects the commit enforcement evaluated (STD-LGS-030); a commit that evaluates none omits it.

```yaml
DAT-RuleBinding:
  classes: { type: list, required: true, description: "content-ids of class and extension versions" }
  sheets: { type: list, required: false, description: "content-ids of sheet versions" }
  tables: { type: list, required: false, description: "content-ids of decision table versions" }
  policies: { type: list, required: false, description: "content-ids of policy set versions" }
  logic: { type: list, required: false, description: "content-ids of logic asset versions" }
  guards: { type: list, required: false, description: "guard evaluations {guard, result}" }
```

### STD-TIME-041 — Re-evaluation modes
- **Clause:** Re-evaluating logic or rules for valid date d MUST support three modes, and the chosen mode MUST be recorded:
  - `as_originally`: use the rule binding of the original commit;
  - `as_effective`: use the versions whose timelines at the current transaction time cover d;
  - `current`: use head versions.

  `as_effective` MUST be the default for restatements and valid-dated recomputation.
- **Grammar / Schema:** —
- **Conformance vectors:** VER-CONF-1885…1899
- **Satisfies:** FR-TIME-063, FR-TIME-064
- **Notes:** Since 1.0-rc8 (DEC-090):
  - **Version per mode.** For a logic asset the versions are those of the asset object:
    - `as_effective` takes the version whose timeline segment covers d;
    - `as_originally` takes the version the original process ran (its journal's logic versions);
    - `current` takes the head.
  - **Recording.** The mode is recorded in the derivation records of the results (STD-TXN-030).
  - **Valid date.** d is the `asof` of the original process.

### STD-TIME-042 — Restatement on a correction branch
- **Clause:** A restatement takes a correcting commit on a branch. It MUST:
  - compute the impact set of that commit (STD-TIME-031);
  - create a branch of kind `correction` from the branch head;
  - re-run, on the correction branch, each process that produced an impacted result, in the order of the processes' first commits, with its recorded invocation and `asof` and the logic versions of the chosen mode (STD-TIME-041, default `as_effective`).

  The results MUST keep the valid times the logic gives them; the source branch is unchanged. The restatement MUST report:
  - the processes re-run;
  - the processes it cannot re-run (results written by direct input with a derivation);
  - for every object the correction branch changed, its old body on the source branch and its new body.

  When the request gives a materiality expression (an L1 boolean over `this`, the new body, and `old`), each change MUST carry its result as `material`.
- **Grammar / Schema:** —
- **Conformance vectors:** VER-CONF-1910…1929
- **Satisfies:** FR-TIME-043, DSN-DVM-322
- **Notes:**
  - The correction branch is merged into the source branch through the ordinary merge (STD-VER-050) once the restatement is accepted.
  - A branch name outside the kind `correction` fails with `MODEL.INVALID_VALUE`.
  - A correction branch is protected (STD-VER-012), so the logic it runs is verified.
  - Since 1.0-rc8 (DEC-090).

### STD-TIME-043 — Compensation proposals
- **Clause:** On the correction branch, the ledger appends (`commit.append`) of a re-run process MUST NOT be committed, since entries are immutable (STD-KIND-021); they are its restated postings. When a restatement asks for `proposals`, it MUST report them as adjustment proposals, one per ledger class, ledger key and currency in which the restated postings differ from the entries the original processes appended:
  - `amounts` holds, per amount field, the restated sum minus the original sum;
  - `corrects` lists the original entries of that key and currency;
  - `valid_at` is the business date of the restatement (`date_policy: open_period`, the default) or the latest `valid_at` of those original entries (`original`).

  Proposals are not appended: a principal appends them as adjustments (STD-KIND-023) once the restatement is accepted.
- **Grammar / Schema:** —
- **Conformance vectors:** VER-CONF-1960…1974
- **Satisfies:** FR-TIME-045, DSN-DVM-323
- **Notes:** Since 1.0-rc9 (DEC-098):
  - **Request.** `restate` takes `proposals: {date_policy}`; without it the result has no `proposals`.
  - **Order.** Proposals are ordered by class, canonical ledger key and currency; a decimal amount has the currency `""`.
  - **Business date.** It is the date of the adapter's current time; an `open_period` proposal for a class with a `period_scope` posts into the period that is open then (STD-KIND-025).
  - **Postings.** With `proposals`, the result also lists the restated postings as `postings`, `{process_id, class, ledger_key, valid_at, body}` in the order made.

### STD-TIME-050 — Emission
- **Clause:** For classes that declare `emit_became_effective`, the implementation MUST emit, at least once, a `BecameEffective` event for each version segment start in the future at commit time, when wall-clock time reaches it. If the segment is removed before then, no event is emitted. A segment start is in the future when it is after the commit date (date granularity) or the commit instant. The event is emitted when the wall clock reaches the start and the segment still starts there with the same version, through the outbox (STD-TXN-050) with effect ID `became-effective/<branch>/<object_id>/<start>` (DEC-041).
- **Grammar / Schema:** —
- **Conformance vectors:** VER-CONF-1900…1909
- **Satisfies:** FR-TIME-052
- **Notes:** Since 1.0-rc6 (DEC-083): the event is released without a commit, so its outbox entry carries no `cseq`; an events subscription of UBTP delivers it after the commits of its branch (STD-PROTO-012).
