# BPA Standard — Conformance (CONF)

> BPA 1.0.0-rc5. Generated by `standard/tools/build_release.py` from `docs/50-system/30-standard/18-conformance.md`; do not edit. Clauses outside this release are omitted.

### STD-CONF-001 — Conformance vector format
- **Clause:** A conformance vector MUST be a canonical JSON document (`DAT-ConformanceVector`) that is independent of implementation language. Vectors are grouped by clause and profile, and packaged with a signed manifest per standard release.
- **Grammar / Schema:** `DAT-ConformanceVector`
- **Conformance vectors:** —
- **Satisfies:** FR-STD-021, FR-STD-022
- **Notes:** —

```yaml
DAT-ConformanceVector:
  id: { type: text, required: true, description: "VER-CONF-nnnn" }
  clauses: { type: list, required: true, description: "STD clause ids exercised" }
  profile: { type: text, required: true, description: "profile name" }
  polarity: { type: enum, required: true, description: "positive | negative" }
  setup: { type: list, required: true, description: "ordered adapter operations establishing the initial state (genesis, classes, objects)" }
  steps: { type: list, required: true, description: "ordered operations with expected results {op, input, expect: {result | error_code, match: exact|subset|hash}}" }
  tags: { type: list, required: false, description: "labels such as `prototype` (the vector is required of the PH-0 prototype) (DEC-032)" }
  determinism: { type: composite, required: false, description: "fixed now, entropy seed, tzdb version" }
  description: { type: text, required: true, description: "what is checked" }
```

### STD-CONF-002 — Adapter protocol
- **Clause:** Implementations are driven by the runner through an adapter speaking UBTP (STD-PROTO) or an in-process adapter with the same message structures. The adapter MUST additionally support the test-only operations `reset`, `set_now`, `set_entropy_seed`, `load_genesis` and `export_state`. It MUST be disabled in production builds.
- **Grammar / Schema:** —
- **Conformance vectors:** —
- **Satisfies:** FR-STD-021, CTR-014
- **Notes:** —

### STD-CONF-003 — Runner report
- **Clause:** The runner MUST produce `DAT-ConformanceReport`, signed by the runner key, listing every vector with its outcome (`pass`, `fail`, `not_applicable` outside the claimed profiles) and failure details.
- **Grammar / Schema:** `DAT-ConformanceReport`
- **Conformance vectors:** —
- **Satisfies:** FR-STD-023
- **Notes:** —

```yaml

  standard_version: { type: text, required: true, description: "BPA version" }
  implementation: { type: composite, required: true, description: "{name, vendor, version, build_hash, backends}" }
  profiles_claimed: { type: list, required: true, description: "profile names" }
  results: { type: list, required: true, description: "{vector, outcome, detail}" }
```

  Conventions of the adapter operations:
  1. Absent inputs take their defaults. `time` is the `cseq` of a commit on the branch (`main` starts at `cseq` 0, empty), and `asof` is a date or an instant. Object and entry identifiers are chosen by the vector.
  2. A step MAY give its input as `input_text`, a JSON text that the adapter parses (duplicate member names are an error, `MODEL.INVALID_VALUE`); vectors carry non-canonical inputs, such as numbers with a fraction, this way. A step MAY carry a `label`. An input value `{"$ref": "<label>/<pointer>"}` is replaced by the member of that step's result at the JSON pointer (RFC 6901). An expectation `{"same_as": "<label>/<pointer>"}` requires the result to equal that value.
  3. In adapter inputs a class is referenced by its name. A trait is a declaration with `trait: true` and `applies_to`, a list of kinds. A ledger class declares `ledger: {key, amounts, double_entry, period_scope}`; `period_scope` names a class whose objects have the fields `start` and `end` (dates, half-open) and `state` (`open`, `closing`, `closed`).
  4. The business time zone of the adapter is UTC; the posting date of an append is the date of `now` (`set_now`).
  5. An expectation `{error_code, details}` also compares the `details` of the error (`DAT-Error`) with `subset` matching: `TXN.HEAD_MOVED` lists the stale objects in `details.objects`, and `VER.MERGE_CONFLICT` lists `DAT-MergeConflict` items `{object_id, kind, path}` in `details.conflicts`, ordered by object and path.
  6. Version hashes, entry hashes, roots, commit identifiers, transaction times and signatures of stateful operations are compared only through `same_as` or through the pure operations, because they depend on the implementation's clock, keys and class identifiers. Before an `exact` comparison of a stateful result, the members `version_hash`, `entry_hash`, `root`, `head` and `versions` are removed from it; since 1.0-rc1 also `commit_id`, `tx_time`, `parents`, `created_from`, `evaluated_at`, `preview`, `base`, `source_head`, `target_head`, `merged_commit`, `signature`, `provenance_ref`, `inputs_commitment` and `class_version`, and `signatures`, `proof`, `records`, `heads`, `archive`, `from_commit`, `to_commit`, `cursor`, `snapshots`, `logic_versions`, `commit_ids`, `changes_hash`, `cpu_us`, `peak_memory`, `wall_us`, `asset`, `record_id` and `json_schema`.
  7. Reference values are canonical URIs `ubos://acme/<Class>/<slug>`: the adapter's tenant is `acme` (since 1.0-rc1).
  8. The adapter's physical clock reads `now`: a commit's `tx_time` is `now`, or one microsecond after the `tx_time` of the head it extends when that is not earlier (STD-TIME-001). The initial commit of a branch has no `tx_time`. The default initiator is `did:ubos:acme:01900000-0000-7000-8000-000000000002` (since 1.0-rc1).
  9. A snapshot of a branch is selected by at most one of `time` (cseq), `commit` (commit identifier), `tag` and `tx_time` (instant), or by `evaluated_at` (a map from branch to commit identifier, STD-TIME-015); none selects the head (STD-VER-090) (since 1.0-rc1).
  10. The adapter's node is `did:ubos:acme:01900000-0000-7000-8000-000000000001` with key `did:ubos:acme:01900000-0000-7000-8000-000000000001#k1` from the seed of 32 bytes `0x01`; `rotate_node_key` adds `#k2`, `#k3` … Every commit record `{vae, branch, parents, cseq, tx_time, root, signatures}`, the subset of `DAT-Commit` that the adapter keeps, is signed by the current node key (since 1.0-rc1).
  11. Logic runs as host programs, the in-process binding of STD-ISA-007: objects of class `Logic` with tier `host` whose `source` is `{functions: {name: {params, body, retryable, max_depth}}}`. A statement is one of `{let, value}`, `{do, args, as}` (an instruction; `args` is JSON whose strings are L1 expressions), `{if, then, else}`, `{each, in, body}`, `{repeat, body}`, `{try, catch, as}` (the caught error is `{code}`), `{return}` and `{fail, message}`. Besides the ABI, programs may call `sys.uuid`, `sys.random_bytes {n}` and the journaled test instruction `adapter.observe {name}` (since 1.0-rc1).

### STD-CONF-011 — Algorithm registry
- **Clause:** Algorithm identifiers for hashes, signatures and AEAD are registered by the standard. Version 1.0 registers `sha256`, `ed25519`, `aes-256-gcm` and `xchacha20-poly1305`. Adding an algorithm is a minor release. Implementations MUST verify content produced with every registered algorithm of their major version. AEAD content is given as key, nonce (12 bytes for `aes-256-gcm`; 24 bytes for `xchacha20-poly1305`, which applies HChaCha20 to the first 16 bytes and ChaCha20-Poly1305 of RFC 8439 to the rest), associated data and ciphertext with the 16-byte tag appended. A tag that does not verify fails with `PROOF.VERIFICATION_FAILED`; an unregistered algorithm is rejected (`MODEL.INVALID_VALUE`) (DEC-042).
- **Grammar / Schema:** —
- **Conformance vectors:** VER-CONF-6200…6209
- **Satisfies:** FR-PROOF-012, NR-SEC-004
- **Notes:** —

### STD-CONF-030 — Standard change process
- **Clause:** Every change to the standard MUST be proposed with rationale, clause diffs and new or changed vectors. Changes are classified as `patch` (errata, clarifications without behaviour change), `minor` (additive) or `major` (breaking). A change is published only with its vectors, and an erratum MUST reference the clause and vectors affected.
- **Grammar / Schema:** —
- **Conformance vectors:** —
- **Satisfies:** FR-STD-011, FR-STD-012, AR-033
- **Notes:** Since 1.0-rc2 (DEC-067): a released vector that asserts a limit of its release (an instruction or operation not yet available) is superseded by the release that lifts the limit. The superseded vector keeps its identifier and content, stays in the released version's manifest, and is listed with its reason in `standard/vectors/superseded.txt`, which the release in development excludes from its manifest and coverage and which runners skip. A superseded vector is never replaced under its identifier. Since 1.0-rc3 (DEC-071): the same applies to a released vector that asserts the whole instruction catalogue of its release (STD-ISA-001) when a later release adds an instruction or an error code; the generator keeps the released expectation of such a vector.
