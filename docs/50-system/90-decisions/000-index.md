### DEC-060 — In-process host and host services on PostgreSQL (PH-1 step 7, part 7a)
- **Status:** Accepted · **Date:** 2026-10-03
- **Context:** PH-1 step 7 (EXIT-1-02, EXIT-1-13) brings the in-process host and the CTR-002 host services on PostgreSQL for gate 1a, Forge `check`, `types` and `test`, and the ten gate-1a scenarios (UBS-PH-1 §2, §3). The kernel of steps 3–6 kept everything a host owns in local stand-ins: the local key provider and blob directory (DEC-047), the node record with a seed in the settings (DEC-059), a deterministic process seed, no connectors or models (`LOGIC.NOT_AVAILABLE`), effects left in the store outbox for the adapter's `outbox` and `ack`. AR-031 lets `ubos-node` depend on `ubos-dvm` (and `ubos-proto`) only, and `ubos-version` sign at flush through the store (DEC-059).
- **Decision:**
  1. **Host boundary in `ubos-dvm`.** `ubos_dvm::host` defines the CTR-002 services as traits — `Clock`, `Entropy`, `Secrets`, `Connectors`, `Models`, `OutboxSink`, `Jobs`, `Telemetry`, with `BlobStore` and `KeyService` of the engine crates — bundled as `Services`, and the host API of CTR-001 as `Vae`: `begin_process`, `invoke_port`, `read`, `query`, `commit`, `merge`, `preview`, `replay`, `export`, `import`, `verify`, `explain`, `reflect` over the engine, reading the clock and firing due timers before every operation, releasing the outbox to the host after it, and emitting one telemetry event per operation. The engine carries the services: a process is seeded from `entropy.fill` and the seed is recorded with the process, so a replay needs no host; `call.connector` and `ask.model` run through the services and are journaled before use (`program::journaled`), so a replay serves the recorded result and never calls the host (SCN-011 A1); without services the instructions stay `LOGIC.NOT_AVAILABLE` and the conformance adapter is unchanged. Deterministic services (`FixedClock`, `SeededEntropy`, a recorder) serve tests (DSN-FRG-202). The engine persists the class declarations with the VAE (`genesis`) and reopens an existing VAE (`open_existing`); hosts always learn the process identifier of an invocation.
  2. **Crate `ubos-node`.** The PostgreSQL implementations (host layer, UBS-ARC-07 §2): the tenant registry (`tenant`, `vae`; DSN-NOD-401, -402) read as the owner role; the key hierarchy root KEK → tenant KEK → derived keys (DSN-NOD-131): the tenant KEK is stored wrapped by the root KEK (XChaCha20-Poly1305, root from `UBOS_ROOT_KEK` or a file, the development key otherwise), data keys and node signing keys are derived with HKDF-SHA-256 and never stored, data key generations rotate (FR-IAM-033); the node signer (DSN-NOD-134) installed on the store, so the version layer signs commit records with the VAE's registered DID `did:ubos:<authority>:<vae id>` and its public key history in `node_key`; the blob table (DSN-NOD-320, -321), secrets sealed under the current data key and resolved only inside connector execution (DSN-NOD-130), connectors registered in the node as the allow-list (DSN-NOD-301, -302), the event log receiving released effects (DSN-NOD-201, -202), jobs with leases, retries and poison (DSN-NOD-220, -221, -223), telemetry redacted to operational members (DSN-NOD-610, -611); migration `0006_host.sql` with row-level security on the tenant tables. Models stay `AI.PROVIDER_UNAVAILABLE` until PH-3.
  3. **Suite.** `ubos-node-suite` (SUITE-NOD-HOST, `verify/reports/suite-nod-host/`) exercises every service, tenant isolation of blobs and secrets, signed records through the key hierarchy, key rotation, reopening, journaled connector calls replayed without the host, and runs in CI.
  4. **Gate 1b** builds the Server on these services: UBTP, sessions and local credentials, schedules, OpenTelemetry export, health, backup and PITR.
  5. **Forge (part 7b).** A Forge project is a directory with `forge.toml` (`[project]`: name, version, vae, abi, branch) and YAML (or JSON) sources under `model/` (`classes`, `value_types`), `logic/` (`assets`: bodies of `Logic` objects), `seed/` (`changes`), `tests/` (`tests`), with `sheets/`, `components/`, `views/` and `docs/` reserved for gate 1b (DSN-FRG-002); `forge init` writes a skeleton that checks and tests. `forge check` runs parse → model (the class registry, one declaration at a time to name the file) → sheets and tables (a warning: gate 1b) → scripts and static analysis (the analyser of the verification gate, DSN-FRG-004) and port implementations → seed data (committed file by file into an in-memory VAE), every stage in one run, findings with file, line, rule, severity and stage (DSN-FRG-101). `forge types` writes `types.ts` and `types.rs` for classes, value types and ports, versioned by branch and model hash (DSN-FRG-102). `forge test` runs `scenario` (vector-style steps with labels and `advance` of the clock), `unit`, `port` and `property` (generated arguments, an L1 invariant over the result) tests against an in-memory VAE built from the model and seed under the deterministic services of part 7a (DSN-FRG-201…203), reports JSON and JUnit XML with the genesis and seed roots and the function coverage per asset (DSN-FRG-204), and signs a verification record per asset with the verifier key (`--key`, or ephemeral; the key-form DID is the signer) binding the asset hash, ABI, checks, test counts, coverage and the inferred capabilities (DSN-FRG-103). Every command takes `--json`; exit status 0, 1 (findings or failures) or 2 (usage) (DSN-FRG-001). The incremental build graph of DSN-FRG-003 is not needed at gate 1a: one pass checks a project in milliseconds; the cache by input hash comes with `forge dev` (gate 1b).
  6. **Scenarios (part 7c).** The ten gate-1a scenarios are a Forge project (`verify/scenarios/`, written by `tools/gen_scenarios.py`) of scenario tests run by `forge test` through the host API with the deterministic services, in memory and on a fresh VAE of PostgreSQL (`forge test --backend postgres`). `forge test` builds every test its own fixture from the model and seed (DSN-FRG-203), mocks connectors from the test (`connectors: {name: {operation: response}}`, DSN-FRG-202), exposes the effects released to the host as the pseudo-operation `released_effects`, and runs a step `concurrent: n` times at once (on PostgreSQL in waves of 16 writers, each in its own adapter on the VAE; SCN-005 A1). Two kernel additions the scenarios needed: `revert` takes `resolutions` like a merge (`source` keeps the reverted value, `target` the later change; SCN-018 step 2) and reverts the chunk commits of a bulk process together with it (STD-TXN-070); dependents stay reported, not reverted (STD-VER-071). Outside gate 1a and recorded in the report: SCN-003 step 3 (a governance sheet: rules, gate 1b), SCN-002 postcondition 2 (JSON Schema: the SDKs of gate 1b; `forge types` gives TypeScript and Rust), SCN-018 A1 (dependent processes: event triggers, gate 1b).
- **Consequences:** Conformance stays at 1,227 of 1,227 on both backends (the adapter has no services); the storage suite 20/20 and the escape suite 382/382 are unchanged. The metering record counts connector calls. A host program may now call connectors and models when a host registers them. The table of UBS-SYS-NOD gains the in-process host of gate 1a. Part 7b: `verify/reports/forge-7b/` holds the skeleton's check and test reports (4 of 4 tests, reproducible roots) and the one-error-per-stage check; CI runs `forge init`, `check`, `types` and `test` on every push. The DVM's acceptance of Forge-signed records at activation (DSN-FRG-103 acceptance 1) joins the install path of gate 1b. Part 7c: EXIT-1-13 is met on the workstation (`verify/reports/exit-1-13/`: 22 of 22 scenario tests on PostgreSQL and in memory, main and alternate flows), and the final signed EXIT-1-02 reports replace the interim ones (`verify/reports/exit-1-02/`: 1,227 of 1,227 on PostgreSQL and in memory); both are re-run on the reference environments at step 9. CI runs the scenarios on both backends. Step 7 is complete.
- **Alternatives considered:** Running the host services from a separate process over UBTP was rejected for gate 1a: the plan verifies the scenarios through the in-process binding, and the Server of gate 1b adds the transport. Storing the node signing seed in the settings as before was rejected: the key hierarchy keeps every private key derived in memory. A separate migration set for the host tables was rejected because sqlx runs one migrator per database; the tables live in the kernel migrations with the host as their only writer.
- **Affects:** UBS-SYS-DVM, UBS-SYS-NOD, UBS-SYS-FRG, CTR-001, CTR-002, DSN-DVM-251, DSN-DVM-560, STD-VER-071, STD-TXN-070, VER-SCN-1000, DSN-FRG-001, DSN-FRG-002, DSN-FRG-003, DSN-FRG-004, DSN-FRG-101, DSN-FRG-102, DSN-FRG-103, DSN-FRG-201, DSN-FRG-202, DSN-FRG-203, DSN-FRG-204, DSN-NOD-130, DSN-NOD-131, DSN-NOD-134, DSN-NOD-201, DSN-NOD-202, DSN-NOD-220, DSN-NOD-221, DSN-NOD-223, DSN-NOD-301, DSN-NOD-302, DSN-NOD-320, DSN-NOD-401, DSN-NOD-402, DSN-NOD-602, DSN-NOD-610, DSN-NOD-611, DSN-FRG-202, STD-CTX-011, STD-PROOF-010, DEC-047, DEC-059, EXIT-1-02, EXIT-1-13

### DEC-061 — Verification close-out of gate 1a (PH-1 step 8, parts 8a–8c)
- **Date:** 2026-10-03 · **Status:** Accepted
- **Context:** PH-1 step 8 (DEC-038) closes the verification of gate 1a: EXIT-1-04 (properties at a million cases), EXIT-1-05 (simulation seeds and 30 clean nights), EXIT-1-06 (durability under injected crashes), EXIT-1-08 (replay on three platforms) and EXIT-1-11 (coverage, mutation score, dependency graph). Thirty consecutive nights and three platforms are calendar and runner conditions that no single session meets, and the crates carried no unit tests: the suites (vectors, scenarios, properties, escape cases, storage and host suites) were the tests. The owner confirmed the plan on 2026-10-03 and part 8a with the default suggestions.
- **Decision:**
  1. **Step 8 in three parts.** 8a: the property set VER-PROP-0100 and EXIT-1-11 (this record). 8b: the simulation suite SUITE-DVM-SIM (`ubos-sim`) and the fault suite SUITE-DVM-FAULT (`ubos-fault`) on PostgreSQL, a million seeds and 10,000 injected crashes on the workstation. 8c: the replay corpus of ≥ 10,000 processes with recorded outcome hashes (`verify/replay/`), the `ubos-replay` tool, and the nightly workflow (simulation seeds, long properties, mutation shards, replay on Linux x86-64, Linux ARM64 and macOS ARM64) whose results accumulate the 30 nights and the three platforms. Each part is one pull request.
  2. **Kernel property set (VER-PROP-0100).** `ubos-props` gains five properties beside the four of PH-0: `index_rebuild_equality` (every read of every object and ledger key at every commit and several dates through the kernel indexes, `time: cseq`, equals the read through the state rebuilt from the commit records, `commit: id`; the root verifier finds nothing; DSN-DVM-005, DSN-DVM-092), `diff_cost_bound` (a tree diff after `c` changes reads at most `2·(h+1)·(3·c+1)` nodes of a tree of height `h`, and lists exactly the changed keys; DSN-DVM-230), `merge_ledger_completeness` (after a merge the target ledger holds its own entries followed by every entry of the branch in branch order, dense sequences, same balance; DSN-DVM-242, STD-VER-052), `balance_bitemporal` (the balance read at any `(asof, cseq)` is the sum of the entries with `valid_at ≤ asof` committed at or before `cseq`, backdated entries included; DSN-DVM-420, DSN-DVM-421, STD-TIME-020) and `cursor_completeness` (pages of a query under concurrent creates, updates and ends return the first page's snapshot exactly once, in order with ties by object id; DSN-DVM-908). Long mode is `--cases 1000000`; CI keeps 10,000 cases per property. Merge determinism, timeline non-overlap and root history independence are the PH-0 properties re-run at a million cases.
  3. **Kernel crates and test bodies.** The core crates of EXIT-1-11 are the eleven kernel crates `ubos-types`, `ubos-crypto`, `ubos-tree`, `ubos-time`, `ubos-model`, `ubos-expr`, `ubos-version`, `ubos-store`, `ubos-runtime`, `ubos-proof` and `ubos-dvm` (UBS-ARC-07). The test bodies are integration tests that run the existing suites in process: every BPA 1.0-rc1 vector in memory and the gate-1a scenarios (`crates/ubos-forge/tests/`), and a sample of every property (`ubos-props`); CI runs them on every push. No unit tests are written for the score: a mutant survives only when no vector, scenario or property notices it, which is the question EXIT-1-11 asks.
  4. **Coverage.** `verify/tools/coverage.sh` runs the suite binaries instrumented by cargo-llvm-cov in release mode, in memory and on PostgreSQL (vectors, scenario check/types/test, properties, escape suite, storage suite, host suite, round trip), and `verify/tools/coverage_by_crate.py` reports line coverage per crate and the kernel total against the 85% threshold. Coverage of the tool and suite binaries themselves (`ubos-forge`, the `bin/` files) is reported but not part of the criterion.
  5. **Mutation score.** `verify/tools/mutants.sh` runs cargo-mutants over the kernel crates with the test bodies above (`--test-package ubos-forge --test-package ubos-dvm`). The workstation measures shards (`--shard k/n`) of the mutants, reported with the sample size; nightly CI (8c) runs every shard and accumulates the full score. A mutant that times out counts as detected (the tests stop an endless loop); unviable mutants are excluded, as cargo-mutants does.
  6. **Reports.** `verify/reports/exit-1-04/` (property report at a million cases) and `verify/reports/exit-1-11/` (coverage summary and per-crate JSON, mutation outcomes per shard, dependency check). The ENV-REF-SERVER runs of step 9 do not repeat these: properties, coverage and mutation score are platform-independent.
  7. **Simulation (part 8b, SUITE-DVM-SIM).** `ubos-sim` is the deterministic simulator of DSN-DVM-516: every seed builds 2–4 nodes (engines) over one shared in-memory store whose lock plays the branch sequencer's, 1–3 branches, six contended objects and two contended ledger keys; a seeded scheduler picks every step (reads, updates against the versions read, serializable transactions with a declared read set, appends, clock jumps forwards and backwards on one node) and injects crashes into the storage flush — an aborted flush (the transaction rolls back) or a crash after the flush applied (the commit exists, the acknowledgement is lost, the node restarts with empty caches). Nodes retry `TXN.HEAD_MOVED` and `TXN.READ_SET_CHANGED` up to five times (DSN-DVM-513). The checker verifies after steps and at the end: linear history per branch (dense `cseq` from the fork point, parent chain), no lost acknowledged commit, unacknowledged commits equal to the crashes after apply, gap-free ledger sequences, and the serializable-history check in the manner of Elle (one version chain per object from the commits' write sets, read sets that were the head at commit). `--inject lost_ack` seeds the defect NR-DUR-001 forbids (acknowledge without applying) for the checker's sensitivity. CI runs 2,000 seeds; the gate run is a million seeds on the workstation; the nightly 10,000 seeds (step 8c) accumulate the 30 clean nights.
  8. **Fault injection (part 8b, SUITE-DVM-FAULT).** `ubos-fault` runs WL-MIXED-OLTP worker processes on a PostgreSQL VAE, each appending every acknowledged commit to its own `fsync`ed log, and injects node crashes (SIGKILL of every worker process at a random moment) and, alternating with them, power loss of the server (`pg_ctlcluster … stop -m immediate`: every server process killed without a checkpoint, then `pg_ctl start`). After every event the recovery check runs on the quiet store (the workers are dead until it ends) and verifies every acknowledged commit at its `cseq` with its identity and versions, dense `cseq`, and the roots of the new commits; every `--verify-every` events the index and sequence verifiers rebuild the branches; a commit the store holds without an acknowledgement is one whose acknowledgement the crash lost, counted and never partial. The gate run is 10,000 events (5,000 of each kind) on the workstation; CI runs 40 SIGKILL events (a check whose work grew with the commits the live workers kept making had stalled the first long run: the node now crashes whole and the check is bounded by the commits of one interval) (a service container cannot be power-cycled); the ENV-REF-SERVER run follows at step 9. The workstation's PostgreSQL uses `recovery_init_sync_method = syncfs` (a 13 s per-file `fsync` walk of the data directory at every crash start otherwise).

### DEC-068 — BPA 1.0-rc2 UBTP: envelope, handshake, mutate, query, subscriptions, flow control and bindings (step 10, part 10d)
- **Date:** 2026-10-15 · **Status:** Accepted
- **Context:** Part 10d of PH-1 step 10 (DEC-064) writes the reference model and the vectors of STD-PROTO-001, -002, -010, -011, -012, -013 and -020. - **Decision:** The clauses are clarified as follows (text in the clauses):
  1.   6.   3. **Cursors.** A cursor binds the query hash, the branch, the snapshot commit and the position, signed with HMAC-SHA-256 under a key derived from the VAE authority until the node host supplies the tenant key (step 14; DSN-DVM-908). A cursor of another query or branch, or with a wrong tag, is `QRY.INVALID_QUERY`; cursor expiry (`INT.CURSOR_EXPIRED`) follows retention in step 14.

Queries over a branch with a parent line, with a tag or transaction-time coordinate, or whose expressions reach other objects (`ref`, `exists`) use the resolved view.

### DEC-074 — Row filters for list queries: residual post-filter with the order-by pushdown (step 13, part 13d)
- **Date:** 2026-10-15 · **Status:** Accepted
- **Context:** DEC-065 item 3 deferred the row-filter technique of list queries (RSK-013, NR-PERF-008) to step 13 after measurement: the crate's partial evaluation where it is stable, otherwise residual predicates derived by `ubos-authz`. DSN-DVM-820 asks for a residual predicate pushed into index scans and a post-filter for what cannot be pushed, with scan limits enforced. Partial evaluation in `cedar-policy` 4.13 is an experimental feature (`partial-eval`) behind a feature flag with an unstable API. Step 13b implemented the post-filter (every candidate row of a query with a principal is authorized for `read`; denied rows are left out and logged); step 13a's index path read every row of the key range up to the scan budget, so a selective order needed the whole range. DEC-073 also left to 13d the rebuild of an index over existing objects and the `order by` pushdown, and step 13c found that a merge into an overlay from a branch of another line panicked for want of a merge base.
- **Decision:**
  1. **Row filters.** In PH-1 the policy set is applied to the candidate rows as a residual post-filter, after the index scan and the `where` (DSN-DVM-820's "residuals it cannot push"). The cost is bounded by the order-by pushdown (item 2), not by the size of the class. Partial evaluation, or residual predicates derived by `ubos-authz` and pushed into the scan, are revisited when the crate's partial evaluation stabilises or when the ENV-REF-SERVER run of VER-BENCH-2000 fails MET-PERF-016; DSN-DVM-820 carries a phase note.
  2. **Order-by pushdown.** When a query over one class orders by the indexed field of its best bound, ascending, the index scan reads `offset + limit` rows in key order (at least 128) and the page is complete once that many rows pass the `where`, the valid-time, state and liveness checks and the row filter; otherwise the scan is repeated with four times the rows, up to the scan budget (`QRY.SCAN_LIMIT` beyond it). Every other query reads its key range up to the budget as before (DEC-073 item 4). Stable ordering (FR-QRY-072) holds: the index orders by `(value key, object identifier)`.
  3. **Index rebuild.** `declare_index` on a class that has instances rebuilds the index over the head objects of every branch (`Store::put_field_rows`) and records, per branch, the head commit of the rebuild (`index_since`, persisted with the VAE); the planner uses the index on a branch only at or after that commit, and on a branch created later from a served commit; a query at an earlier commit scans within its budget. Rows of later heads are written at flush as before.
  4. **Merge base.** A merge, preview or change-set merge between branches without a common ancestor (an overlay, whose history starts empty under its parent line, and a branch of another line) fails with `VER.MERGE_NOT_ALLOWED` ("no merge base") instead of panicking; merging into an overlay is done from a branch created from the overlay.
  5. **Benchmark.** `ubos-bench query` (crate `ubos-dvm`, binary `ubos-bench`) is the MET-PERF-016 suite: one class with two declared indexes and a unique key, the queries `eq`, `range`, `eq_filter` (with a policy set), `page2` (the cursor) and `key`, in memory or on PostgreSQL; the workstation report is `verify/reports/exit-1-17/workstation/`, the ENV-REF-SERVER run follows at step 19 (VER-BENCH-2000).
- **Consequences:** The released vectors stand. `Engine::index_since` and the store method `put_field_rows` exist in both backends; DSN-DVM-820 is met in PH-1 by the post-filter path and the pushdown; RSK-013 stays open until the ENV-REF-SERVER run.
- **Alternatives considered:** Enabling the crate's experimental partial evaluation was rejected for PH-1 (unstable API, a feature flag of a security component); deriving residual predicates in `ubos-authz` was deferred: the measured post-filter meets the target on the workstation datasets and the pushdown removes its dependence on the class size. Rebuilding indexes with rows valid from the first commit was rejected: a historical query would see the rows of heads that did not exist, or miss objects whose head then differed.
- **Affects:** DSN-DVM-820, DSN-DVM-902, DSN-DVM-903, DEC-065, DEC-073, RSK-013, VER-BENCH-2000

### DEC-076 — PH-1 step 15: events, jobs and schedules, parts 15a–15e
- **Date:** 2026-10-16 · **Status:** Accepted
- **Context:** Step 15 of gate 1b (DEC-063) builds events, jobs and schedules (CAP-EVT-01…05; the PH-1 clauses DSN-NOD-201…204, -208, -209, -220, -221, -223…-226, -228…-230) with EXIT-1-17 (MET-PERF-017, NR-PERF-012) and NR-DUR-006. - **Decision:**
  1. **Parts.** 15a: `outbox_claim`, `outbox_ack` and `due_effective` in the kernel and store; the node's releaser with claims and per-key order replacing the synchronous release, delivery after recovery; the event log queryable by type, object and time with the retention sweep; leadership leases with fencing tokens; became-effective driven every second (DSN-NOD-201, -202, -208, -228). 15b: subscriptions, the listener registry, handlers as processes, retry policies, dead letters (DSN-NOD-203, -204, -209). 15c: jobs as objects with leases, heartbeats and fencing, poison detection, the sweeper, operator controls, fairness, bulk processes as jobs (DSN-NOD-220, -221, -223, -229, -230). 15d: schedules with exactly one firing per slot, hot changes, pause and resume, missed slots (DSN-NOD-224…-226). 15e: SUITE-NOD-EVENTS, SUITE-NOD-JOBS, the workstation runs of MET-PERF-017, NR-PERF-012 and NR-DUR-006 and the EXIT-1-17 report. One pull request per part.
  2. **Jobs are objects; leases are runtime state.** A job is a System-kind `Job` object (FR-EVT-031) whose type, payload, state, attempts, last error and priority change by committed processes. The lease holder, lease expiry, heartbeat and fencing token live in the `job` table, the runtime hint DSN-NOD-220 allows, so that a heartbeat is not a commit; the sweeper rebuilds missing rows from the objects (FR-EVT-032).
  3. **Deliveries are jobs; dead letters are dead jobs.** Each handler delivery is a job, and an item that exhausts its retry policy is a job in state `dead` with its last error. Deliveries, scheduled firings and bulk processes share one mechanism for leases, retries and poison detection.
  4. **Platform classes.** `Subscription`, `Schedule` and `Job` are classes of the namespace `ubos.platform` that the node declares in every VAE it opens; they are not part of BPA 1.0 and add no clauses or vectors. Step 16 packages them as a genesis Buk.
  5. **Handlers in PH-1.** Handlers of kind port and logic. Webhook, connector and workflow handlers follow in PH-2 together with delivery masking (DSN-NOD-205), so that no payload leaves the node unmasked (phase note on FR-EVT-021).
  6. **Clarifications.** Dead letters are retried, cancelled or annotated; their payloads are never edited (FR-EVT-052 over DSN-NOD-209). The catch-up policies are FR-EVT-041's `skip`, `fire_once` and `fire_all` (DSN-NOD-225's none, last and all). The leader drives became-effective events every second (NR-PERF-012 over DSN-NOD-208's minute). Claims round-robin across tenants and respect per-tenant concurrency limits now (FR-EVT-034); DSN-NOD-222's latency bound stays in PH-2. Poison is a job failing with the same error signature three times (on one node, across its attempts).
  7. **Sagas.** Bulk processes (DSN-DVM-560, kernel `bulk`) run as jobs in 15c; saga coordinators follow DSN-DVM-564 in PH-2 (phase note on DSN-NOD-230).
- **Consequences:** Phase notes on DSN-NOD-201, -202, -208, -209, -220, -221, -223, -225, -230, FR-EVT-021 and FR-EVT-041. The kernel gains `outbox_claim`, `outbox_ack` and `due_effective`; migration 0009 and later ones add the releaser's claims, the leadership leases and the schedule state. The benchmark report lives in `verify/reports/exit-1-17/` beside step 13d's; the reference-environment runs remain in step 19.
- **Alternatives considered:** Jobs as table rows only (gate 1a) were rejected (FR-EVT-031 asks for objects, and a lost table would lose jobs); a commit per heartbeat was rejected (write amplification with no evidence value); adding the platform classes to BPA 1.0 was rejected (the release is near and these are host behaviours); webhooks in PH-1 without masking were rejected (payloads would leave unmasked).
- **Affects:** DSN-NOD-201, DSN-NOD-202, DSN-NOD-208, DSN-NOD-209, DSN-NOD-220, DSN-NOD-221, DSN-NOD-222, DSN-NOD-223, DSN-NOD-225, DSN-NOD-230, FR-EVT-021, FR-EVT-034, FR-EVT-041, FR-EVT-052, EXIT-1-17, NR-DUR-006, DEC-063

  3. **SDK authentication in PH-1.** The SDKs implement password sign-in, sessions with refresh and API keys; browser OIDC with PKCE and OAuth client credentials follow with DSN-NOD-103 and DSN-NOD-151 in PH-2, device-bound tokens with DSN-NOD-107 in PH-4.
  4. **Compatibility.** The SDKs negotiate the protocol version in the handshake and pass the version-skew cases; a test against two node minors runs when protocol 1.1 exists.
  5. **Bindings.** For the SDKs, "all PH-1 bindings" of EXIT-1-15 are HTTP, WebSocket and SSE. The in-process binding is offered to the Rust SDK by an optional adapter crate under the node's licence, not by the SDK itself.
  6. **Licences.** The SDKs are Apache-2.0: `@ubos/sdk` in `packages/sdk-ts/`, `ubos-sdk` stating its licence in its manifest. Their dependency `ubos-proto` (with `ubos-types`) is AGPL today, as `verify/` depends on AGPL crates; the legal review before a public release (DEC-019) settles a permissive licence for the protocol crates. The engineering UI goes to `packages/eng-ui/` under AGPL-3.0-only.
- **Consequences:**
  - Phase notes on DSN-SDK-010 and DSN-SDK-014.
  - Migration 0015 adds the tables `upload` and `file`; the node depends on the `fastcdc` crate (MIT).
  - New configuration keys `files.max_upload_mb` and `files.download_link_seconds`.
  - 17d: the SDK suites found three defects of the node's UBTP binding, fixed with the step: an idempotency key was remembered per session, so a client retrying in a new session after a lost reply ran the mutation again (STD-TXN-040 scopes a key by principal; the binding now carries the key into the kernel's process, whose record is written with the commit, and replays a recorded key before it checks `base`); a read ignored the message's `commit` coordinate; a `timeline` without `from` failed. A `--genesis` file may also name branches to create.
  - 17c: browsers reach the node across origins through the reloadable key `server.cors_origins` (none by default; preflights answered, the session, tus and download headers exposed, bearer credentials only, no cookies); the WebSocket binding takes the tenant from the `tenant` query parameter as well as `Ubtp-Tenant`, since browsers cannot set WebSocket headers.
- **Alternatives considered:**
  - Whole-file assembly at the end of an upload was rejected: memory grows with the file; cutting chunks as bytes arrive keeps at most one chunk per upload.
  - Download through the UBTP channel was rejected: links let browsers and other clients fetch files with plain HTTP and ranges.
  - Waiting for PH-2 to offer OIDC in the SDKs was not needed for gate 1b: local identity covers the acceptance scenarios.
- **Affects:** DSN-NOD-320, DSN-NOD-321, DSN-NOD-327, FR-FILE-011, FR-FILE-012, DSN-SDK-010, DSN-SDK-011, DSN-SDK-014, DSN-FRG-501, EXIT-1-15, DEC-063

### DEC-079 — PH-1 step 18: the thirteen PH-1 scenarios over UBTP, parts 18a–18d
- **Date:** 2026-10-17 · **Status:** Accepted
- **Context:**
  - **The step.** Step 18 of gate 1b (DEC-063) runs the thirteen PH-1 scenarios (SCN-001, SCN-009, SCN-017 and the ten gate-1a scenarios) over UBTP on the single-node Server, with EXIT-1-19 (scenario report) as its exit criterion.
  - **A gap in the Protocol.** The gate-1a scenarios (DEC-060 item 6) call the kernel through the host API: besides reads, commits and queries they create branches, open, submit, approve and merge change sets, preview merges, revert processes, run bulk processes, and inspect the effective class, port dispatch, commit records, ledger entries, process records, journals, metering records and replays. UBTP 1.0 as released in BPA 1.0-rc3 (STD-PROTO-001…020) has none of these messages, so a client of the Server cannot run the scenarios. AR-033 puts the standard before the code.
  - **Time.** SCN-006 and SCN-007 need time to pass (a price becoming effective, a schedule firing); the Server runs on the system clock.
- **Decision:**
  1. **Parts.** One pull request per part.
     - 18a: BPA 1.0-rc4, opened by the scope rule of gate 1b on the base 1.0-rc3: STD-PROTO-014 (the versioning requests of `mutate`: `create_branch`, `change_set`, `merge`, `revert`, `bulk`, each with its permission and the uniform result `{process_id?, commits, versions, warnings, result}`) and STD-PROTO-015 (the introspection requests of `query`: `class`, `dispatch`, `commit_info` with the state root, `merge_preview`, `ledger`, `process` with journal and metering record, `replay`); notes on STD-PROTO-010 and -011; the reference model and 47 vectors; the release notes and manifest; the owner's signed tag `bpa-v1.0.0-rc4`.
     - 18b: the kernel's in-process binding (`ubos-dvm/src/ubtp.rs`) and the Server implement 1.0-rc4; SUITE-NOD-PROTO replays the new vectors over the WebSocket and HTTP bindings; the dev preset gets a test clock that an operator endpoint advances (production presets keep the system clock).
     - 18c: the Rust and TypeScript SDKs offer the versioning operations of IF-SDK-004 and the introspection queries, with cases in SUITE-SDK-PROTO.
     - 18d: a scenario runner on the Rust SDK runs the thirteen scenarios over UBTP on a single-node Server on PostgreSQL, over WebSocket and over HTTP; SCN-001 and SCN-017 also use the operator commands; the EXIT-1-19 report in `verify/reports/exit-1-19/`; the run joins CI.
  2. **Names.** The versioning and introspection requests are named after the adapter operations they map to (STD-CONF-005); `create_branch` and `commit_info` avoid the coordinates `branch` and `commit` of the message body.
  3. **Change sets.** The client names the change set's `id`, since the change set is an object of the target branch (STD-VER-020); the approver of `approve` and `reject` is the session's principal, never a member of the message.
  4. **Environments.** The EXIT-1-19 run of 18d is made on the development workstation and in CI; its run on ENV-REF-SMALL joins the reference runs of step 19, as for EXIT-1-18 (DEC-077).
- **Consequences:**
  - BPA 1.0-rc3 stays frozen as tagged (DEC-072); `spec/` and `vectors/` hold 1.0-rc4.
  - Until 18b, SUITE-NOD-PROTO skips the vectors of STD-PROTO-014 and -015, and the kernel's conformance test runs only the vectors of the releases it implements (DEC-070).
  - 18a found that replaying a port process whose logic updates its object diverges in the reference model (`changes_hash`): the base of the update is taken from the current head rather than from the journaled snapshot (STD-CTX-012). The 1.0-rc4 replay vector uses a read-only port; the defect is recorded for correction with the kernel check of 18b.
- **Alternatives considered:**
  - Running the scenarios through the in-process binding only was rejected: EXIT-1-19 asks for UBTP on the Server.
  - New message types (`branch`, `merge`, …) beside `mutate` and `query` were rejected: they would change the envelope of STD-PROTO-001 and every binding, while new request kinds of `mutate` and `query` reuse idempotency, `base`, authorization and emits.
  - An operator-only scenario harness that bypasses UBTP was rejected for the same reason as the in-process run.
- **Affects:** STD-PROTO-010, STD-PROTO-011, STD-PROTO-014, STD-PROTO-015, IF-SDK-004, EXIT-1-19, DEC-063, DEC-072

### DEC-080 — The content-addressed build cache of `forge` after PH-1
